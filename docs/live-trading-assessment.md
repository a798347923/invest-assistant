# 实盘操作功能评估与实施方案（草案 v0.1）

> 状态：**评估中，未实施**。本文档供决策评审，通过后再进入开发。
> 目标：把现有「模拟盘逻辑」扩展为可操作真实账户的能力，券商为东方财富证券。

---

## 1. 目标与边界

- **要做什么**：买点触发 / 每日 AI 建议 → 经风控过滤 → 生成并执行实盘买卖，覆盖「建仓 / 加仓 / 减仓 / 清仓」，并进入现有复盘与预测校准闭环。
- **不做什么**：不做高频、不做融资融券/打新/条件单、不承诺收益、不代客理财；所有参数由账户主人设定。
- **基本原则**：风控与审计先行；默认最小权限（默认关闭、默认 dry-run、默认每笔人工放行）。

## 2. 现状盘点（可复用资产）

| 已有能力 | 实盘可复用方式 |
|---|---|
| 1 分钟盘中轮询、买点/失效价提醒 | 信号源直接复用 |
| 模拟盘（自动买入、15:40 AI 建议、次日开盘执行） | 交易逻辑与撮合口径直接复用为"意图生成器" |
| 交易日志 + 清仓复盘（高级模型）+ 预测校准 | 实盘成交写入同一日志体系（source=live），复盘/校准自动覆盖实盘 |
| 风控相关配置模式（paper 段） | 扩展为 live 段（见 §5） |
| 通知（邮件/微信） | 指令单推送、成交通知、对账告警复用 |

## 3. 通道可行性（关键结论）

**东方财富无面向个人的公开交易 API。** 个人实现程序化交易的三条通道：

| 通道 | 可行性 | 说明 |
|---|---|---|
| **A. QMT / Ptrade（官方量化通道）** | ✅ 唯一推荐的自动化通道 | 东财证券支持 QMT/Ptrade；通行门槛：**50 万资产 + C4 风险测评 + 半年交易经验**，免费开通（以客户经理口径为准）。两种接入方式见 §4-B |
| **B. 客户端/网页 UI 自动化**（easytrader 类） | ⚠️ 不推荐 | ①违反券商用户协议风险；②客户端更新即失效；③误单风险高；④**无法完成程序化交易报备**（见 §6） |
| **C. 东方财富量化终端（emquant）** | 待核实 | 官方另有"东方财富量化终端"（研究/仿真/实盘一体），门槛与服务对象需向东财核实 |

**待用户核实清单（联系东财客户经理时逐条问）**：
1. QMT / Ptrade 是否可开通、门槛（是否 50 万）、费用与时长；
2. 是否支持 **QMT 极简模式**（外部 Python 经 xtquant 下单）——部分渠道已停新申请（2026-07 起），标准模式是否仍可；
3. 程序化交易报备由券商哪个环节办理；
4. 是否支持"内置策略 + 信号文件"的落地方式（见 §4-B-②）。

## 4. 方案设计

### 4.0 公共分层架构

```
信号层(复用)            风控层(新增)                 执行器(可切换)             账务与审计
─────────────────────────────────────────────────────────────────────────────────────
买点/失效价/每日建议  →  金额/仓位/频次/价格保护  →  manual   : 指令单+人工下单  →  trade_journal(live)
大盘环境/经验/校准       白名单/时段/熔断开关           qmt_file : 信号文件+QMT策略     实盘持仓(PositionService)
                        幂等/重复下单防护              qmt_xtq  : xtquant 直连       每日对账 job
                                                                                       ↓
                                                                       清仓复盘(已有) + 预测校准(已有)
```

**核心数据模型增量**：`order_intent`（指令单）——字段：id、日期时间、code、side（买/卖）、qty、参考价、来源（买点/日报/人工）、风控结果、状态（待执行/已确认/已成交/已放弃/拒绝）、成交价、成交数量、幂等键。

### 4.1 路线 A：半自动指令单闭环（无前置条件，建议先做）

**流程**：
1. 现有信号触发（买点/日报建议/失效价）→ 风控层逐条校验；
2. 通过 → 生成指令单并**推送**（邮件+微信："买入 601166 400 股，参考价 18.4，理由…"）+ 面板「实盘执行」页展示；
3. 用户在东财 App 手动下单；
4. 回面板点「已成交」（填实际成交价/数量）或「放弃」/「部分成交」；
5. 已成交 → 写入实盘持仓（建仓/加仓/减仓/清仓走既有 PositionService）与交易日志 → 后续复盘/校准自动衔接。

**优点**：零合规风险、当天可用、天然人工复核；同时积累"系统建议 vs 实际执行"的差异数据。
**局限**：非全自动（需用户点击）。

### 4.2 路线 B：QMT 通道（若开通）

| 接法 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| ① xtquant 直连（极简模式） | 本机运行 QMT 极简客户端，我们的进程经 xtquant 直接下单/查持仓 | 集成度最高 | 依赖极简模式开通；QMT 客户端需常开 |
| ② 信号文件 + QMT 内置策略 | 我们的系统写 `orders.json`（指令+风控结果），QMT 里跑一个几十行的小策略轮询文件并下单 | 不依赖极简模式；QMT 内运行稳定 | 需在 QMT 里维护一个小策略；双向回执用第二个文件 |

**上线纪律（B 路线强制执行）**：
1. `live.dry_run=true` 连续 **≥2 周**：指令只记录不发送，与人工执行结果对比一致率 ≥95%；
2. 小额真实验证（单笔 100 股级别，1–2 周）；
3. 才允许打开 `dry_run=false`。

### 4.3 配置草案（`config.yaml` 新增 `live` 段）

```yaml
live:
  enabled: false            # 实盘总开关（默认关，需显式开启）
  executor: manual          # manual（默认）/ qmt_file / qmt_xtquant（预留）
  dry_run: true             # 只记录不发送（默认开）
  confirm_mode: each        # each=每笔人工放行 / auto=自动执行
  max_order_amount: 5000    # 单笔金额上限（元）
  max_position_weight: 0.2  # 单标的最大市值占比
  max_daily_orders: 4       # 单日下单笔数上限
  max_daily_buy_amount: 20000
  price_deviation_pct: 1.0  # 限价偏离现价上限（超过即拒单）
  whitelist: watchlist      # watchlist / candidates / both
  trading_window: ["09:35-11:25", "13:05-14:55"]
  circuit_breaker_index_pct: -1.5   # 指数急跌熔断（当日暂停自动执行）
```

## 5. 风控清单（必须项，全部有单测）

| # | 规则 | 默认 | 失败动作 |
|---|---|---|---|
| 1 | 全局开关 `enabled` | 关 | 不生成指令 |
| 2 | dry-run | 开 | 只记录不发送 |
| 3 | 每笔人工放行 `confirm_mode=each` | 是 | 推送等待确认 |
| 4 | 单笔金额上限 | 5,000 元 | 拒单 |
| 5 | 单标的市值占比上限 | 20% | 拒单/缩减数量 |
| 6 | 单日下单笔数 / 买入金额上限 | 4 笔 / 2 万元 | 当日暂停 |
| 7 | 价格偏离保护（限价 vs 现价） | ±1% | 拒单 |
| 8 | 标的白名单（自选/候选池） | 自选池 | 拒单 |
| 9 | 交易时段限制（含避开开盘前 5 分钟） | 09:35–11:25 / 13:05–14:55 | 不发送 |
| 10 | 涨跌停 / 停牌 / ST 拒单 | 是 | 拒单 |
| 11 | 大盘急跌熔断（指数日内跌超阈值） | -1.5% | 当日暂停自动执行 |
| 12 | 幂等键（同一信号不重复下单） | 是 | 去重 |
| 13 | 超时未成交处理 | 15 分钟未成交撤单 | 撤单并告知 |
| 14 | 每日对账（系统记录 vs 券商实际持仓/资金） | 收盘后 | 差异告警 |
| 15 | 全量审计（意图→风控→委托→成交/放弃） | 是 | — |

## 6. 合规与安全注意

1. **程序化交易报备**：A 股程序化交易需通过券商向交易所报备（含策略类型、最高申报速率等）。QMT 开通流程通常包含该环节；自建 UI 自动化无报备渠道——这是不推荐路线 B(UI) 的核心理由之一。
2. **账户安全**：QMT 路径下交易密码在券商客户端登录，不落盘到本工具；任何情况下本工具只读"成交回报"，不保存交易密码。
3. **资金边界**：仅操作自有资金账户；风控默认值从严，放宽需手动改配置。
4. **免责**：所有建议由 AI/规则生成，实盘操作与盈亏由账户主人自行决策承担；工具不承诺收益。

## 7. 验收标准（可测试）

| 项 | 标准 |
|---|---|
| 风控单测 | §5 每条规则对应单测（拒单/通过场景）≥15 个用例，全绿 |
| 幂等 | 同一信号在重试/重启场景下不产生重复指令 |
| dry-run 期 | ≥2 周；指令与人工执行一致率 ≥95%；期间零误发 |
| 对账 | 每个交易日收盘对账，差异为 0 或触发告警（非静默） |
| 审计 | 每笔意图的完整链路（生成→风控结论→执行/放弃→成交）可在面板追溯 |
| 全链路演练 | 模拟信号 → dry-run → 小额真实成交 → 对账平衡，四步全部记录在案 |
| 复盘衔接 | 实盘清仓后自动进入经验库；预测校准自动覆盖实盘建议 |

## 10. 决策与首期实现（2026-10-18）——历史记录

> 2026-10-18 晚更新：**全自动部分已取消**（见 §11）；本节保留为历史记录。

**用户决策**：UI 路线 = **东财 PC 客户端**；**全自动 + 半自动同时保留，各自独立开关**。

### 已实现

- `config.live`：总开关 + 双模式开关（`semi_auto_enabled` / `full_auto_enabled`）+ 限额/时段/白名单/偏离/熔断；
- `order_intent` 表（迁移 `b5c2d3e4f5a6`）：代码/方向/数量/限价/模式/风控结论/状态/成交回填/幂等键/审计；
- 风控（`engine/live.py`，14 个单测）：总开关、模式开关、`ui_pc` 要求、单笔金额、当日笔数/买入金额、
  价格偏离、交易时段、ST、涨跌停区间、自选池、幂等；
- CLI：
  - `live probe`：导出东财 PC 客户端窗口/控件树 + 截图（只读）；
  - `live create / list / confirm / fill / cancel`：半自动闭环；
  - `live run`：全自动执行入口（`dry_run` 时只标记，不提交）。

### 双模式语义（互不重复）

- 每张指令单带 `mode`（`semi` / `auto`）；
- **半自动**：生成指令 → 用户在东财客户端手动下单 → `live confirm` / `live fill` 回填；
- **全自动**：`live run` 把 `auto` 指令交给 UI 执行器；必须同时满足
  `live.enabled`、`live.full_auto_enabled`、`executor=ui_pc`、`dry_run=false`，且 UI 适配器已校准；
- 两个开关都开时，默认创建 `semi` 指令（显式 `--mode auto` 才走全自动），避免同一信号双下单。

### 全自动上线前置（硬性）

1. 打开并登录东财 PC 客户端，运行 `invest-assistant live probe`（可加 `--title 东方财富`）；
2. 把 `data/live_probe/ui_tree_*.txt` 与截图提供给开发方，实现下单页适配器（填写/提交/回执）；
3. `dry_run=true` 观察 ≥2 周：指令与人工执行一致率 ≥95%、零误发；
4. 小额验证（100 股级别）1–2 周；
5. 才允许 `full_auto_enabled=true` + `dry_run=false`。

### 安全边界

- 不保存交易密码；只驱动已登录的客户端；
- 默认单笔 5,000 元 / 单日 4 笔 / 单日买入 2 万元；
- 全部指令与状态变更入库审计；执行失败标记 `failed` 且不自动重试；
- UI 自动化存在券商协议/合规与版本失效风险（见 §3/§6），启用即视为已知悉。

### 探针结果（2026-10-18 实测）

- **主终端「东方财富终端」是 CEF 自绘**：UIA/win32 仅暴露 15 个外壳控件，无法定位行情/交易控件；
- **独立交易窗口「东方财富证券」**：Win32 标准按钮/树/下拉可枚举（股票/信用/开放基金/OTC/期权/港股/美股、
  重新登录/锁屏/系统），但**买入表单（代码/价格/数量）是自绘控件、无独立句柄**；
- 结论：下单只能走「**窗口坐标校准 + 键盘输入 + 剪贴板回读校验**」，窗口移动/缩放即拒绝执行。

### 校准与填单流程（已实现）

1. 打开交易窗口并进入买入页（保持窗口位置/大小不变），运行：
   ```
   invest-assistant live calibrate
   ```
   依次把鼠标移到 证券代码 / 买入价格 / 买入数量 / 买入按钮 /（可选）确认按钮，输入 `ok` 回车；
   坐标保存到 `data/live_ui_calibration.json`（含窗口位置，位置变化即拒绝执行）。
2. **填单演练（只填不提交）**：
   ```
   invest-assistant live fill 600519 100 1500
   ```
   逐字段 Ctrl+A/C 回读校验，截图保存到 `data/live_orders/`；回读不一致立即停止。
3. 人工核对截图后提交（危险操作，需 `--yes`）：
   ```
   invest-assistant live submit --yes
   ```
4. 全自动：`live run` 串起 填单→校验→提交；必须已校准 `confirm` 点，否则**拒绝提交**（fail closed）。

## 11. 决策更新（2026-10-18 晚）：取消全自动 UI 代理

**决定**：取消全自动下单（UI 代理）。

**原因**：
- 东财 PC 交易页为自绘控件，只能依靠「坐标 + 键盘模拟」，窗口位移/DPI/输入法/确认弹窗都可能导致误单；
- 可靠性不足以承载真实资金；且存在券商协议与程序化交易报备风险。

**已移除**：UI 探针/坐标校准/自动填单/自动提交（`live probe|calibrate|fill|submit|run`）、
全自动配置（`full_auto_enabled` / `executor` / `dry_run`）、pywinauto/Pillow 依赖，以及本地探针截图。

**保留（可靠部分）**：半自动指令单闭环——
指令单（风控/幂等/审计）→ 人工在东财客户端下单 → `live confirm` / `live fill` 回填 →
实盘账本/复盘（后续接入）。

**后续**：若将来满足 QMT/官方 API 门槛，再评估全自动；在那之前不碰自动下单。

### 半自动闭环（2026-10-18 实现）

```
模拟盘买入成功 ──► 实盘买入指令单（预算 = live.max_order_amount，默认 5000 元）
实盘持仓规则触发 ──► 实盘卖出指令单（整仓；卖出不受白名单/时段限制）
        │
        ▼
人工在东财 APP/客户端下单 ──► live fill 回填成交
        │
        ▼
自动写入实盘持仓（买：建仓/加仓；卖：减仓/清仓）+ 交易日志
        │
        ▼
清仓自动进入复盘经验库 / 校准闭环
```

- 触发镜像需要 `live.enabled=true` + `live.semi_auto_enabled=true`；买入镜像可关（`live.mirror_paper_entries=false`）；
- 同一标的同一方向每天最多一张指令单（幂等键），不会重复推送；
- 回填买入的默认退出规则：止盈 12%（P2：到 +10% 自动生成“减半卖出”指令，余仓目标 12%）/ **止损按信号日机械止损价换算**（回踩=近10日低−1×ATR14、突破=近10日低×0.95；无机械价时回退 8%）/ 最长持有 30 天（`live.default_*` 可改）；
- 实盘买入前检查近期公告：命中 减持/解禁/立案/调查/问询/预亏/下修/风险警示/退市/处罚 → 跳过该买入指令（公告取不到则放行）；
- 卖出指令关联具体持仓（`ref_position_id`），回填时按数量减仓/清仓；
- 账本更新失败不会阻塞成交事实，但会在指令单备注中标记「账本更新失败」。

## 12. 决策更新（2026-11-01）：恢复自动执行，但改走「MuMu 里的东财 App + ADB」

**决定**：恢复"和模拟盘一样功能"的实盘自动执行；载体从 **PC 客户端** 改为 **MuMu 模拟器里的东财 App**，
用 **ADB + UIAutomator 控件树** 驱动。默认 `dry_run=true`（只填单、不提交）。

### 12.1 为什么这次不是重蹈 §11 的覆辙

§11 取消的是「PC 客户端 + 屏幕坐标 + 键盘模拟」：交易表单自绘、无控件句柄，窗口一移就错位。
本方案的定位依据完全不同：

| 维度 | §11 取消的方案 | 本方案 |
|---|---|---|
| 载体 | 东财 PC 客户端（CEF/自绘） | MuMu 里的 Android App |
| 定位 | 屏幕坐标（窗口位移/DPI 即失效） | `uiautomator dump` 的控件树，按 text/class/bounds 查找 |
| 填单校验 | 剪贴板回读（受输入法影响） | 回读**控件文本** `node_at(x,y).text` |
| 依赖 | pywinauto + Pillow | 只用 adb + 标准库 |
| 失败行为 | 坐标错 = 静默下错单 | 任一步失败即中止，**零提交** |

### 12.2 已实现

- `engine/live_app.py`：`AdbDevice`（设备原语）→ `Screen`（控件树解析/定位）→ `AppExecutor`（填单/校验/提交）→ `LiveAppService`（与指令单集成）；
- CLI：`live doctor`（adb/设备/App 自检）、`live probe`（导出控件树与截图，用于校准文案）、`live exec <id>`（单条执行）、`live run`（批量执行 pending）；
- 配置：`live.executor=ui_app`、`live.dry_run=true`、`live.app.*`（包名/设备/按钮文案/等待秒数）；
- 审计：每步写 `order_intent.note`，每步截图存 `data/live_orders/<id>_<step>.png`；
- 测试：`tests/test_live_app.py` 12 个用例（控件定位、回读不一致中止、dry-run 零提交、确认弹窗缺失判未核实、非数字输入拒绝、状态流转）。

### 12.3 安全契约（fail-closed，全部有测试）

1. 定位失败 / 输入框不足 / 回读不一致 / 找不到提交按钮 → **中止，绝不提交**，指令记 `failed`；
2. `dry_run=true` 时不点提交，指令保持 `pending`（演练通过）；
3. 提交后不推测成功：看到成功文案才算 `verified`，否则 `submitted` + 「待人工核对」；
4. 提交只点一次，**不自动重试**（避免重复下单）；
5. 只驱动已登录 App，不保存交易密码。

### 12.4 上线节奏（硬性）

1. MuMu 里安装并登录东财 App → `live doctor` 显示"已安装"；
2. 进入交易-买入页 → `live probe` 导出控件树，确认 `买入/卖出/确定` 文案与输入框数量（必要时改 `live.app.*`）；
3. `dry_run=true` 连跑 ≥2 周：每次填单与人工判断一致率 ≥95%，零误填；
4. 小额真实验证（100 股级）1–2 周；
5. 才允许 `dry_run=false`。

### 12.5 已知缺口（不要忽略）

| 缺口 | 影响 | 计划 |
|---|---|---|
| 提交前不校验「可用资金/可卖数量」 | 券商端拒单或部分成交，系统仍记为已提交 | 下一步读交易页的"可买/可用"文案做前置校验 |
| 无自动撤单（挂单未成交） | 限价单可能挂一整天 | 加 15 分钟未成交撤单（§5 #13 已有约定，未实现） |
| 无自动对账 | 系统持仓与券商实际可能不一致 | 每日收盘读"持仓/委托"页对账 |
| App 改版导致文案变化 | 定位失败 → 中止（不会误单，但功能不可用） | `live probe` 快速校准 |
| 程序化交易报备 | 券商协议与监管要求（§6） | 属账户主人已知风险，不在代码内解决 |
